    17→    17→=== Page 2 ===
    18→    18→1. Passage a une application web 
    19→    19→Cette version du plan adapte le projet BS-Lokossa d'une application mobile Flutter vers une application web 
    20→    20→Next.js / React. Toutes les fonctionnalites du cahier des charges sont conservees. Le backend Supabase reste 
    21→    21→identique. Cette version integre les corrections structurelles suivantes : phase P0 scindee en P0A (Infrastructure) 
    22→    22→et P0B (Architecture), tests de validation a la fin de chaque phase, Design System, documentation BDD et API, 
    23→    23→securite renforcee et strategie Git. 
    24→    24→ 
    25→    25→1.1 Avantages de l'application web pour BS-Lokossa 
    26→    26→• Acces immediat : aucune installation requise, depuis n'importe quel navigateur (PC, telephone, tablette) 
    27→    27→• Mises a jour instantanees : une modification deployee est visible par tous sans action de l'utilisateur 
    28→    28→• Economies : 0 USD pour le deploiement (Vercel gratuit) contre 25 USD pour le Play Store mobile 
    29→    29→• Equipe plus large : les developpeurs React/JS sont bien plus nombreux que les developpeurs Flutter/Dart 
    30→    30→• PWA optionnelle : l'app web peut etre installee sur l'ecran d'accueil du telephone comme une vraie app 
    31→    31→• Maintenance simplifiee : pas de versions APK, pas de validation externe 
    32→    32→ 
    33→    33→1.2 Stack technique adoptee 
    34→    34→• Frontend : Next.js 14 (App Router) + React + TypeScript 
    35→    35→• Styles : Tailwind CSS + shadcn/ui (composants prebuilt accessibles et reutilisables) 
    36→    36→• Backend : Supabase (PostgreSQL + Auth JWT + Storage + Realtime) — identique a la version mobile 
    37→    37→• Notifications push : Web Push API + Service Worker + Firebase Cloud Messaging web 
    38→    38→• Paiement : FedaPay JavaScript SDK (MTN MoMo, Moov Money, carte bancaire) 
    39→    39→• Hebergement : Vercel (gratuit pour Next.js) avec domaine personnalise 
    40→    40→• Securite : Zod (validation), Rate Limiting, CSP, CORS, cookies HTTP-only, RLS Supabase 
    41→    41→• Monitoring : Sentry (erreurs) + Vercel Analytics + Supabase Logs 
    42→    42→ 
    43→    43→1.3 Repartition des roles 
    44→    44→• Developpeur Frontend 1 (Next.js / React / TypeScript) — pages, interfaces utilisateur, navigation, formulaires 
    45→    45→• Developpeur Frontend 2 (React / TypeScript) — composants reutilisables, Design System, state management 
    46→    46→• Developpeur Backend 1 (Supabase / SQL) — schema BDD, RLS, triggers PostgreSQL, Edge Functions 
    47→    47→• Developpeur Backend 2 (Next.js / Securite) — API Routes, middleware, authentification, crons 
    48→    48→• Developpeur Integration (Dev 5) — FedaPay SDK web, WhatsApp API, Web Push, SMTP, filigrane PDF

  1082→  1082→5. Bonnes pratiques techniques 
  1083→  1083→Regles et recommandations techniques a respecter tout au long du projet pour garantir la qualite, la securite et 
  1084→  1084→la maintenabilite de l'application BS-Lokossa. 
  1085→  1085→5.1 Architecture de la base de donnees 
  1086→  1086→• Creer le diagramme Entite-Association (ER) via dbdiagram.io avant tout developpement (obligation P0B) 
  1087→  1087→• Rediger un dictionnaire de donnees : type, contrainte, description, valeurs possibles pour chaque colonne 
  1088→  1088→• Definir les index sur les colonnes tres requetees (matricule, email, niveau_acces, institution) 
  1089→  1089→• Nommer les tables en snake_case pluriel : members, audit_logs, cash_transactions, uniform_orders 
  1090→  1090→• Toutes les tables doivent avoir un champ id (uuid), created_at et updated_at (timestamps auto) 
  1091→  1091→• Les cles etrangeres doivent avoir une contrainte ON DELETE (CASCADE ou SET NULL selon le cas) 
  1092→  1092→ 
  1093→  1093→5.2 Documentation des API Routes 
  1094→  1094→• Chaque API Route Next.js doit etre documentee : methode HTTP, parametres, reponse JSON, codes d'erreur 
  1095→  1095→• Utiliser Zod pour valider les donnees entrantes de chaque route (schema strict cote serveur) 
  1096→  1096→• Les routes protegees verifient le token Supabase Auth en debut de fonction (getServerSession ou 
  1097→  1097→createServerClient) 
  1098→  1098→• Retourner des codes HTTP semantiques : 200 (OK), 201 (cree), 400 (invalide), 401 (non auth), 403 (interdit), 
  1099→  1099→404 (introuvable), 500 (erreur serveur) 
  1100→  1100→• Documenter les permissions : quel niveau d'acces peut appeler chaque route 
  1101→  1101→ 
  1102→  1102→5.3 Design System 
  1103→  1103→• Creer les composants de base des P0B : Button, Input, Textarea, Select, Modal, Table, Badge, Pagination, Toast, 
  1104→  1104→Skeleton, Avatar 
  1105→  1105→• Definir les tokens Tailwind dans tailwind.config.ts : couleurs FEUA, espacements, rayon de bordure, ombres 
  1106→  1106→• Chaque composant doit etre accessible (aria-label, role, focus visible) et responsive 
  1107→  1107→• Documenter chaque composant avec ses props TypeScript et ses cas d'usage (Storybook optionnel) 
  1108→  1108→• Ne jamais dupliquer un composant : tout element reutilisable va dans components/ui/ et est importe 
  1109→  1109→ 
  1110→  1110→5.4 Securite renforcee 
  1111→  1111→• Rate Limiting : limiter les routes publiques (login, inscription, paiement) avec upstash/ratelimit ou similaire 
  1112→  1112→• Content Security Policy (CSP) : configurer les headers dans next.config.js pour bloquer XSS 
  1113→  1113→• Validation Zod : valider TOUTES les donnees entrantes cote serveur (ne jamais faire confiance au client) 
  1114→  1114→• Sauvegardes automatiques : activer les sauvegardes quotidiennes Supabase (plan Pro) ou exporter 
  1115→  1115→manuellement chaque semaine 
  1116→  1116→• Journalisation centralisee : tous les appels API Routes sont loggues (Supabase Logs + Sentry) 
  1117→  1117→• Surveillance des performances : activer Vercel Speed Insights pour detecter les pages lentes
